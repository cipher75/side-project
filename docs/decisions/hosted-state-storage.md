# 호스팅 상태 저장과 갱신 방식

## Decisions

- 호스팅은 줄인 상태를 Upstash Redis(Vercel Marketplace)에 둡니다. 해시 하나에 PC마다 필드 하나를 두어, PC끼리 서로의 쓰기를 덮어쓰지 않습니다. REST로 호출해 연결을 유지하지 않습니다.
- 갱신은 기기의 화면이 주기적으로 조회하는 방식입니다. 일이 있으면 4초, 없으면 15초마다 가져오고, 탭이 숨겨지면 멈춥니다.
- PC의 로컬 서버는 상태가 바뀔 때, 그리고 살아 있음 신호로 20초(연결된 세션이 없으면 60초)마다 올립니다. 호스팅은 신호 간격의 세 배가 지나면 그 PC의 소식이 끊긴 것으로 봅니다.
- 오래 소식이 없는 PC는 6시간 뒤 보기 요청에서 지웁니다. 지난 기록은 두지 않습니다.
- 새 npm 패키지 없이 `fetch`로 Redis REST API를 호출합니다.

## Boundaries

- 저장되는 것은 [local-first-deployment](local-first-deployment.md)가 허용한 줄인 상태뿐입니다. 호스팅 서버도 호출 입력이 남은 상태는 받지 않고 거절합니다.
- 여러 사용자나 사용자별 분리를 위한 저장 구조가 아닙니다.

## Why

Vercel 서버리스는 서버 메모리가 요청 사이에 유지되지 않고, Hobby의 함수 최대 시간이 300초라 SSE 같은 오래 유지되는 연결이 5분마다 끊깁니다. 상태를 외부 저장소에 두고 짧은 조회로 가져오면 어느 인스턴스가 응답해도 같은 결과가 나오고 사용량 계산이 쉽습니다. 조회를 일이 있을 때만 잦게 하면 무료 한도(Vercel Hobby 함수 호출 월 100만, Upstash 무료 월 50만 명령) 안에서 개인용 규모를 감당합니다.

## Reconsider when

- 무료 한도를 반복해서 넘거나, 갱신이 4초보다 빨라야 한다는 요구가 생길 때
- 여러 기기를 늘 켜 두는 사용이 보편적이 되어 조회 비용이 문제일 때
- Vercel이 서버리스에서 오래 유지되는 연결을 한도 안에서 안정적으로 지원할 때

## Still-rejected alternatives

- SSE나 WebSocket으로 계속 연결 — Hobby 함수 최대 시간(300초)마다 끊기고, 연결이 길수록 사용 시간이 늘어납니다.
- Vercel Edge Config — Hobby에서 쓰기가 월 100회뿐이라 자주 바뀌는 상태에 맞지 않습니다.
- Vercel Blob — 캐시 때문에 몇 초 단위 갱신에 맞지 않습니다.
- 서버 메모리에 상태 저장 — 서버리스는 요청마다 다른 인스턴스가 처리할 수 있어 상태가 갈라지거나 사라집니다.

## Evidence worth preserving

- Vercel 공식 문서로 확인한 한도: Hobby 함수 호출 첫 1,000,000건, 함수 최대 시간 300초, Edge Config 쓰기 100회. Upstash 무료는 월 50만 명령, 데이터 250MB.
- 2026-10-22 실제 Upstash Redis(무료, `iad1`, 리소스 `office-state`)에 연결했습니다. Production에서 토큰 거절(토큰 없음, 보내기 토큰으로 조회, 보기 토큰으로 전달 모두 401)과 보기 토큰 조회, PC의 로컬 서버 전달이 실제로 돌았고, 저장된 상태에는 줄인 라벨만 있었습니다.
- 같은 프로젝트에 다른 Redis 통합이 붙어 있으면 둘 다 `REDIS_URL`을 넣으려 해서 Upstash 연결이 실패합니다. 이 앱은 `REDIS_URL`을 읽지 않으므로 쓰지 않는 쪽의 연결을 풉니다.
